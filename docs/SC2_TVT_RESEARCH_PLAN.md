# SC2 完整 TvT AI：调研结论与技术方案

调研日期：2026-09-29。状态：方案已整理，尚未开始部署、数据处理或训练。

本文汇总本轮公开文档、原始论文与 DI-star 源码调研，并纳入用户确认的环境和资源约束。文中“建议”“候选”“验收目标”均不代表已实施或已实测。

许可阅读结果另见 [SC2 AI 与 DI-star 许可要求整理](SC2_LICENSE_REQUIREMENTS.md)，区分游戏软件、开源代码、录像和权重的授权范围。

## 1. 目标、范围与授权边界

开发《星际争霸 II》完整 1v1 人族对人族（TvT）神经网络 AI，支持与内置人族电脑对战、当前策略及历史策略自我对战，以及用户使用人族进行实时对战。在可用资源内持续提高水平。

学习路线固定为：历史人类 TvT 录像 → 匹配版本引擎解码 → 随机初始化网络的监督学习／行为克隆（BC）→ 当前正式版强化学习（RL）→ 自我对战 → 固定条件评测 → 受控优化。允许复用开源代码、接口和框架；现成模型仅用于环境验证或参照，不能代替自己训练模型。

- 最终交付必须支持开发、验收时确认的 **SC2 最新正式版本**，不能永久停留在 DI-star 的旧版本，也不以 PTR 代替正式版。
- 每轮实验固定具体 build、数据版本、地图及依赖；正式版更新后建立新的实验序列，不在一轮实验中自动切换。
- 策略只使用己方合法观测，保留战争迷雾。训练专用额外价值信息必须与执行策略隔离。
- 默认保留完整人族动作范围，不用脚本决定开局、生产、侦察或微操。程序可以负责动作转换和合法性。
- 宏观动作、限制兵种和脚本微操只能作为另行说明的可选教学分支，不能擅自替代完整 TvT 目标。
- 本次授权仅涵盖整理文档。安装、克隆、下载录像或模型、修改环境、训练及远程写入仍待用户明确授权。
- 不修改已有 `AGENTS.md`。

### 2.1 100 GB 存储管理

按保守口径，100 GB 上限覆盖本项目新增的代码、依赖环境、历史引擎、地图、录像、缓存、模型、日志及临时文件。下载中间文件、解压峰值以及双系统之间的重复副本均计入，不能以放到 Ubuntu 或临时目录规避限制。用户已有游戏安装单独记录，不擅自清理或改动。

建议先规划不超过 80 GB，留出至少 20 GB 用于下载、解压、检查点保存等峰值。该数值是工作预算，不是已测得需求；C 盘实际剩余空间不足时还需降低预算。

- 先做小样本存储测量，按需获取版本和赛事包，不下载全量多版本客户端。
- 解码缓存采用分片、压缩和显式保留策略；保留原始录像及转换清单以便重建。
- 保留 BC 基线、最佳模型及代表性历史快照，限制冗余日志与中间检查点。
- 每次大规模下载或处理前估算峰值，而不是只计算最终文件大小。
- 当前阶段不删除任何文件；后续清理只针对实施时明确约定的项目生成物。
- 若预计会超过 100 GB，先提交用途、预计峰值、可缩减选项及需要的额外空间，等待批准。

### 4.1 实际 RL 算法

已核实的调用链并非 PPO：

- `rl_loss.py` 计算行为策略与当前策略的概率比，并按动作头截断。
- `as_rl_utils.py::policy_gradient_loss` 调用 `vtrace_advantages`。
- `upgo_loss` 使用 `upgo_returns`；critic 使用 TD(λ) 损失。
- 教师约束方向为 **KL(教师策略 ‖ 当前策略)**，另有开局动作类型约束与熵项。
- DAPO 分支存在，但公开 RL 用户配置的 `use_dapo=False`。
- 小规模配置主要启用胜负奖励；代码支持其他奖励不代表默认实验启用了它们。

基线保留该流程；若以后比较 PPO，必须作为另一个算法实验说明。DI-star 的逐头 V-trace 实现也应与 IMPALA 的一般公式区分。

依据：[RL 损失](https://github.com/opendilab/DI-star/blob/12b1c69350ad41e17895c602a66a52d98dd58452/distar/agent/default/rl_training/rl_loss.py)、[回报与 KL](https://github.com/opendilab/DI-star/blob/12b1c69350ad41e17895c602a66a52d98dd58452/distar/agent/default/rl_training/as_rl_utils.py)、[RL 配置](https://github.com/opendilab/DI-star/blob/12b1c69350ad41e17895c602a66a52d98dd58452/distar/bin/rl_user_config.yaml)、[IMPALA 原论文](https://arxiv.org/abs/1802.01561)。

## 6. 数据来源与处理设计

### 6.1 来源核实与未决统计

[SC2ReSet 记录 14963356](https://zenodo.org/records/14963356) 为 2.0.0，发布于 2025-03-03，文件总量约 4.5 GB，列表包含 2016—2024 年赛事包。发布日期不能视为比赛日期。

2023 年论文描述的是较早数据范围，不能用其总样本数代表扩充后的 2.0.0。本轮未下载录像，因此 **实际 build 分布、去重 TvT 数量、匹配引擎可成功解码数量尚未确认**。后续必须报告按版本、地图和比赛分组后的可用量。[数据集原论文](https://www.nature.com/articles/s41597-023-02510-7)

首选原始 SC2ReSet；不足时再核查公开赛事包，以及用户愿意提供的新版 TvT 录像。原始录像和预处理数据的许可分开记录，不把预处理数据许可自动套到全部原始材料。

### 6.2 数据流水线

1. 建立清单：文件 SHA-256、来源、比赛时间、双方玩家及实际种族、结果、时长、地图、`game_version`、`base_build`、`data_build` 和可获得的 `data_version`。缺失项明确标记。
2. 筛选标准人类 1v1 TvT。首批双方明确选择 Terran；Random 实际为 Terran 单独标记。排除损坏、非标准模式和电脑对局，不因 MMR 缺失直接判低质量。
3. 完全重复按文件哈希去重；不同包装的同场录像结合玩家、时间、地图、长度和事件指纹归组。短局先分类，不无条件删除 rush。
4. 先按比赛组划分，再生成双方视角和序列切片。默认训练／验证／测试为 80／10／10，尽量按比赛系列分组并按版本、地图分层；另留时间或赛事外推集合。
5. 同场双方视角、重复录像、不同解码版本和所有切片必须进入同一集合。归一化、采样统计及 Z 库只用训练集构建。
6. 用匹配的引擎二进制、数据版本及原地图依赖重放，指定玩家视角并保留迷雾。缺依赖的录像隔离，不回退到最新版本解码。
7. 提取动作前观测、动作、时间差；检查同 loop 多命令、长空闲、取消、无效操作及 tag 变化。禁止动作后状态泄漏到输入。
8. 缓存可追溯分片，携带比赛组、玩家、版本及特征 schema。先解码约 100 场，测耗时、失败原因与存储放大率后扩展。

事件解析不等于引擎重建。官方 `s2protocol` 可读头部及事件，但不提供完整平衡规则，tracker 位置也不是全部单位逐帧状态。SC2EGSet 事件数据不能直接替代合法玩家观测。[s2protocol](https://github.com/Blizzard/s2protocol)、[论文预印本](https://arxiv.org/abs/2207.03428)

## 7. 网络与训练架构

流程为：匹配版本录像 → 合法观测与动作 → 随机初始化 BC → 当前版对局采样 → V-trace／UPGO 更新 → 冻结评测与历史快照。

忠实复现的部分：实体、空间、标量分别编码；循环记忆；动作类型、延迟、排队、选择单位、目标单位、目标位置六类自回归输出；分头 SL；行为概率和循环状态记录；教师约束；历史对手池。这与 AlphaStar 的人类数据初始化与多智能体训练路线一致，但不声称复现其规模或实力。[AlphaStar 原论文](https://doi.org/10.1038/s41586-019-1724-z)

### 7.1 个人硬件候选配置

| 项目 | 推荐首版；均待实测 |
| --- | --- |
| 网络 | 实体宽度 128、两层注意力、两层隐藏维 256 的 LSTM，保留六类动作头 |
| SL | batch 2、序列长 32 起步，正确维护循环状态 |
| RL 并行 | 1 场起步，再测 2／4 场；自我对战可能每场两个客户端 |
| 联赛 | 一个学习主策略、冻结 BC 和历史快照，不立即加入多个 exploiter |
| 奖励 | 胜／负／平为主，先不增加大量人工经济奖励 |
| Z | 首条基线固定为空，再单独加入训练集 TvT Z |
| 精度 | 先 FP32 正确性，再测混合精度；概率比、KL、回报优先 FP32 |
| 地图 | 一张打通，再扩至两张；保持精确建造坐标 |
| 训练周期 | 每轮 2 小时有效训练，允许恢复和累计 |

上述缩小是明确的复现差异：原模型配置为三层、隐藏维 384 的 LSTM。不要把缩小版结果写成原配置复现。

Z 中的完整录像未来建造序列只能作为明确的策略条件；在线从训练集库选取或置空，不能读取当前比赛未来或测试录像未来。

默认关闭额外价值信息。启用后，actor 的输入、缓存及归一化独立；验证相同己方观测与循环状态下，仅改变 critic 专用敌方信息不会改变 actor logits。区分循环序列截断、真正终局和时间上限，正确处理 bootstrap。

## 8. 旧版预训练到最新版 RL

| 问题 | 结论与证据边界 |
| --- | --- |
| 旧录像能否解码 | 存在匹配引擎／数据／地图的技术路径；历史下载可用性及本机解码成功率未验证 |
| 观测动作是否对应 | 通用概念可映射，但相同 ID 或名称不能证明语义相同 |
| 迁移策略是否有效 | 经济、侦察与操作可能迁移；开局时机和兵种价值可能失效，属待测假设 |
| 新版 RL／少量新版录像适应 | 方法合理，但没有本项目硬件和数据下的成功保证 |

迁移步骤：

1. 保存原始 ID，并建立按版本的规范化语义层，区分目标形式、施法条件与队列属性。
2. 历史 BC 保留真实资源、时长和转移，可加入版本标识或分桶。
3. 保留可对应的参数，新增动作初始化，移除动作屏蔽，缺失字段带有效性标记。
4. 做新版零更新评测，分清接口错误和策略失配。
5. 用新版真实对局先训练价值分支，再逐步更新策略；教师只约束兼容行为。
6. 在共同合法支持集上重新归一化 KL，不让旧教师永久压制新增能力。
7. 有少量新版录像后，分别比较新版 BC 微调和 RL 混合 BC，不同时改变多个因素。

禁止简单替换旧样本价格、生产时间等数值来假造新版轨迹。新版规则可用于当前动作验证；新版资源、战斗与后续状态必须来自新版引擎。

## 9. 版本与双系统部署

本轮检索到官方正式补丁资料至少到 5.0.16b，但补丁名称不是准确 build。本轮尚未启动用户提供的客户端，因此不将该名称写成已验证的最终目标版本。实施及交付时重新确认最新正式版与地区发布情况。[官方补丁公告](https://news.blizzard.com/en-us/article/24291949/starcraft-ii-5-0-16b-hotfix-patch-notes)

官方说明 Windows 零售版包含 API；公开 Linux 研究客户端下载列表只列到 4.10。本轮读取的 PySC2 和 DI-star 静态版本表到 5.0.9。包装器表过旧不证明新版 API 不可用，但也不能默认升级依赖后全部兼容。[官方客户端列表](https://github.com/Blizzard/s2client-proto)、[PySC2 版本表](https://github.com/google-deepmind/pysc2/blob/master/pysc2/run_configs/lib.py)

### 9.1 推荐分工

- Windows：先验证最新正式版接口、非实时步进训练和双客户端真人实时对战；本机小规模 learner 优先原生运行。
- 已有 Ubuntu：必要时用于已验证版本的历史录像解码、离线 SL 或后续 learner 部署。
- 双系统通常不能同时运行；跨系统工作优先通过带 schema 的缓存和检查点分阶段交接。不能默认同一台机器可同时运行 Windows actor 与原生 Ubuntu learner。
- 不默认安装 WSL 或重装系统。若未来需要同时跨系统运行，应作为单独部署决策说明。
- 真人对战使用匹配版本的客户端，冻结模型并暂停本机训练。最终当前版本验证仍以实际支持该版本的客户端为准。

DI-star 指南报告 Windows 4.10 以前的录像存在迷雾问题，需要样本复核。Linux 离线研究客户端还需手动提供原地图缓存依赖。[小规模指南](https://github.com/opendilab/DI-star/blob/12b1c69350ad41e17895c602a66a52d98dd58452/docs/guidance_to_small_scale_training.md)、[Linux 官方说明](https://github.com/Blizzard/s2client-proto/blob/master/docs/linux.md)

### 9.2 PyTorch 与实验冻结

不沿用 PyTorch 1.7.1 GPU 环境。兼容性候选为 Python 3.10、PyTorch 2.7.1＋CUDA 12.8 wheel；这是可验证的 Blackwell 起点，不是“最新版本”声明。PyTorch 官方确认 2.7 引入 Blackwell 支持，并列出 Linux／Windows 的 CUDA 12.8 构建。[官方发布说明](https://pytorch.org/blog/pytorch-2-7/)、[版本组合](https://pytorch.org/get-started/previous-versions/)

仍需验证旧 NumPy／Protobuf 接口、序列化、多进程、循环网络及前后向算子。`torch.cuda.is_available()` 不能单独作为验收。

每轮记录二进制路径和哈希、`base_build`、`data_build`、`data_version`、地图及依赖哈希、代码 commit、依赖锁、数据清单、配置和随机种子。通过官方 `ResponsePing` 验证实际启动结果，不匹配立即停止。新正式版发布后，旧实验继续按原版本解释，新版另开实验并在交付前验收。[官方协议](https://github.com/Blizzard/s2client-proto/blob/master/s2clientprotocol/sc2api.proto)

## 10. 实施里程碑与最小验证顺序

以下为待授权计划，不是已完成任务。

| 阶段 | 最小验证 | 验收条件 |
| --- | --- | --- |
| M0 当前版接口 | 查实际 build；建立 TvT；观测与动作；双客户端实时连接 | 最新正式版可明确锁定，保留迷雾；失败先解决接口 |
| M1 GPU | 小张量及模型前后向、保存与恢复 | 无架构错误，损失／梯度有限，恢复一致 |
| M2 录像 | 一个版本桶 10 场，再约 100 场 | 版本、视角与动作对齐正确；失败可归因；报告存储放大率 |
| M3 TvT 覆盖 | 起降、附件、队列、变形、技能测试场景 | 所有支持能力有映射；核心机制无静默丢弃 |
| M4 BC | 小样本过拟合，再小时级正式训练 | 各头学习有效，保留集改善，能完整结束对局 |
| M5 最新版 RL | 自训 BC 初始化，固定内置电脑与教师 | 轨迹概率正确，可恢复，无崩溃或超时收益漏洞 |
| M6 自我对战 | 历史池、外部评测、真人对战 | 相对 BC 可解释进步；最新正式版对战稳定 |

M0 失败不能用旧版结果冒充目标完成；M2 失败不启动大规模 BC。测试脚本仅用于接口与机制验收，不进入执行策略。

### 10.1 时间与瓶颈测量

- 部署调试按开发工时记录，可能跨多天或数周，不计作训练时间承诺。
- 数据处理先测双视角每场耗时、失败率和缓存体积，再估算全量；使用可续处理分片。
- 训练默认每轮 2 小时，保存模型、优化器、随机状态、数据游标和对手池状态。
- 评估独立计时；真人对战接近真实局长，大规模评测可能比单轮训练更久。
- 测 1／2／4 场并行的 CPU 单核和总占用、客户端 RAM、显存、温度、功耗、采样吞吐、队列等待和更新速度。
- 初期建议给系统留约 6—8 GB RAM 和显存余量；这是管理目标，不是实测消耗。
- CPU 模拟或解码饱和才考虑增加 CPU worker；GPU 更新饱和才考虑租 GPU。当前版 Windows 采样瓶颈不会因单租 Linux GPU 自动消失。

## 11. 固定评测设计

冻结游戏／数据／地图版本、游戏速度、种族、内置电脑 `Difficulty` 与 `AIBuild`、种子、实际出生位置、模型哈希、策略采样参数、最大局长、超时与重试规则、动作频率和设备。

优先非作弊 `Medium`、`Hard`、`VeryHard`。`CheatVision`、`CheatMoney`、`CheatInsane` 单列，不以“最高难度”混称。[官方难度枚举](https://github.com/Blizzard/s2client-proto/blob/master/s2clientprotocol/sc2api.proto)

无法直接指定出生位置时，通过实际加载结果配对和平衡；固定种子不等于保证跨平台逐帧确定性。

| 类别 | 必须报告 |
| --- | --- |
| 对局 | 胜／负／平、启动和完成局数、超时 |
| 不确定性 | 胜率及 95% Wilson 区间，按对手／地图／出生侧分层 |
| 可靠性 | 崩溃、断连、错误版本和重试；不悄悄剔除失败局 |
| 动作 | 掩码拒绝、协议拒绝、执行错误及分类 |
| 速度 | 游戏 loops/s、玩家决策步/s、完整对局/小时、更新/s |
| 实时 | 观测接收到动作提交的 P50／P95／P99、观测陈旧程度和超期率 |

快速筛查默认 20 局，正式比较至少 100 局并根据区间决定追加；100 局胜 50 局的 95% Wilson 区间仍约 40%—60%。平局和运行失败分别报告，预先约定计分及分母。

- 内置电脑表现：作为外部基准，不换算人类段位。
- 自我对战表现：报告对冻结 BC 和各期快照的交叉胜率；左右互搏约 50% 不证明变强。
- 对人类表现：冻结 checkpoint，记录玩家水平、地图、会话和操作约束；只战胜用户不代表达到某天梯段位。

默认允许 RAW 接口读取己方视野内信息，不附加摄像机限制；报告说明与人类屏幕操作条件不同。决策节奏候选为至少 4 game loops 间隔，密集录像命令的对应方式需单独验证，不静默丢弃。最终延迟阈值由决策节奏与实测结果确定。

## 12. 首批受控优化实验

先冻结可运行基线，每次只改变一个因素；单种子筛查后，对保留方案至少用三个训练种子复核。

| 实验 | 单一变量 | 比较方式 |
| --- | --- | --- |
| A 容量 | 实体编码宽度 128 → 256 | 同墙钟时间，比较性能与吞吐 |
| B 记忆 | 序列长度 32 → 64 | 同训练样本预算，检查中后期及侦察效果 |
| C 教师 | 固定 KL → 预设衰减 | 新版适应收益与基础操作遗忘 |
| D 对手 | 历史池均匀抽样 → PFSP | 池成员不变，同环境样本预算 |
| E 新版示范 | 无辅助 → 固定小比例新版 BC | 同 RL 样本量，额外报告示范量和计算成本 |
| F 推理 | 独立 → 集中批量推理 | 同模型，比较吞吐、策略滞后与延迟 |

首版自我对战默认 50% 当前策略镜像、50% 冻结历史池，始终保留 BC。内置电脑训练先作为前置阶段与独立评测；是否混入联赛另作实验。

所有比较同时记录墙钟时间、环境样本量和更新次数；不得忽略额外示范、评测或超参数搜索成本。

## 13. 后续待验证事项

用户已补充安装路径、100 GB 上限、已有双系统及最终最新版要求，不再重复询问这些信息。剩余事项优先在获得实施授权后通过检查解决：

1. 指定路径中客户端的实际 build、数据版本、地区发布状态以及最新版 API 可用性。
2. C 盘实际剩余空间；Ubuntu 是否已有所需工具、存储位置及跨系统数据交接方式。
3. SC2ReSet 2.0.0 的真实版本分布、去重 TvT 数量、地图依赖与解码成功率。
4. 历史客户端和地图下载可用性；本机 PyTorch 前后向兼容性。
5. 本机持续负载下的采样、更新、内存、显存、磁盘峰值及真人延迟。

下载链接出现在官方页面不等于本轮验证下载成功；公开源码可读不等于本机已经运行通过。当前不租算力、不部署、不训练；下一步应先获得用户对实施阶段的明确授权。
