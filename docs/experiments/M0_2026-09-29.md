## 真人实时运行与问题排查

`m0-human-001` 自动运行 600.078 秒，推进 13416 game loops；观测循环 2359 次，程序侧提交 293 次移动命令，真人客户端收到 136 条动作记录，未收到异步动作错误。两个客户端均以退出码 0 退出，没有强制终止。以上只能说明传输与游戏持续运行，不能证明所有记录都来自成功的人类指令。

用户明确反馈：本机操作，正常战网启动时没有问题；测试窗口和键盘正常、下方面板可点击、单位悬停有响应，但场景内鼠标单选和框选失效。因此这次真人项未通过，不能凭稳定连接判定通过。

- 两客户端采样 RAM 峰值合计约 2.45 GB，CPU 时间分别约 901.75 与 887.92 秒（各进程多核累计，不是墙钟时间）。
- 250 ms 观测周期超期 13 次，占 0.55%；未观察到持续不推进或断连。
- 观测请求往返 P50/P95/P99 约 15/16/32 ms；双方观测批次接收完成到动作确认约 0/15/16 ms。
- 上述首轮时间来自 Windows Python 3.11 的 `monotonic`，出现约 15.6 ms 量化，**0 ms 不代表零延迟**。代码已改用高分辨率 `perf_counter`，需在后续真人复测中重新采集，不能用新代码修饰旧测量。
- 结束前一次 `nvidia-smi` 快照为总 GPU 显存使用 1063 MiB；含桌面及其他应用，既不是项目独占用量，也不是峰值。

真人端开局和终局均为 8 名工人、13 补给，矿物从 50 增至 4710。本轮不能从这些数据推断玩家成功训练过单位或完成建造；需要结合用户症状确认控制通路。

后续受控排查中，改变显示模式或单独移除真人 RAW 配置均未恢复；保持原生真人接口并改真人为房主后，用户确认“单选、框选已恢复”，且生产工人数发生变化。该安排与 [PySC2 原生真人参考流程](https://github.com/google-deepmind/pysc2/blob/master/pysc2/bin/play_vs_agent.py)一致。将它作为本机验证过的部署约束；客户端内部原因未证实，不外推为所有版本/系统的通用结论。没有修改 Windows 缩放、鼠标绑定或兼容性注册表。

`m0-human-002` 在最后一份进度记录（约513秒）中观察到827条真人客户端动作、55名工人和111补给；之后因测试工人损失结束。原脚本未在异常路径汇总 realtime 指标，所以这些只是进度快照，不能视为完整样本统计。已保留该次执行源码副本；最终复测使用新的源码哈希，不覆盖旧证据。

`m0-human-003` 最后进度快照为110.21秒、2423 game loops、55条程序移动命令、0次周期超期；不能用这份局部快照推断整段统计。收到用户确认后立即写入停止请求，报告保留 `passed=false` 和 `Diagnostic stopped by operator request`，表示自动600秒条件未完成，不是新增鼠标或客户端故障。总运行131.70秒包含启动、加载与退出。源码及通信依赖锁哈希与最终提交内容一致；两个测试进程均正常退出，未留下 SC2 进程。

最终人工结论来自用户明确确认，不能用第三轮仅1条客户端动作记录自行推断生产和建造完成。完整10分钟的高分辨率时延分位数及动作生效延迟不在本轮已验收范围。

`m0-smoke-001` 观测点采样到的客户端 RAM 峰值约 1.11 GB；该短场景在约 0.99 秒场景执行时间中推进 1136 loops。它不包含启动/加载，也没有神经网络，**不能作为完整对局或 RL 采样吞吐预测**。

部署调试、接口运行分别记录；没有数据处理、神经网络训练或胜率评测，没有下载录像数据集/模型或安装 PyTorch。验收录像为本轮接口测试产生，不是训练集。
