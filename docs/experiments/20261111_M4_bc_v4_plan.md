# M4 BC v4 方案：把编码器摘要接进选择解码器

状态：**已训练、判据未达成**。日期：2026-11-11；负责人：Ubuntu/DSH；种子 `20261108`。上游：[v3 记录](20261111_M4_bc_v3.md)（含统一后的度量口径）。

## 为什么改这一处

统一口径（批 2、按活跃计数汇总）后，v3 的测试损失按头拆开：

| 头 | 损失 | 权重 | 对总损失贡献 |
| --- | --- | --- | --- |
| selection | 2.6803 | 1.0 | **2.680（50%）** |
| target_unit | 2.6044 | 0.5 | **1.302（24%）** |
| ability | 1.1469 | 1.0 | 1.147（21%） |
| delay | 0.63 | 0.25 | 0.16 |
| target_kind | 0.22 | 0.25 | 0.06 |

两点事实决定选择头的优先级：

1. **它占一半的总损失**，且是唯一有明显行为缺陷的头：测试 precision 0.879 但 recall 只有 0.264，即模型只敢挑目标集合里约四分之一——分布塌到少数最有把握的单位上。F1 在四个模型里从 0.3989 到 0.4225 都上不去，不是训练不足的表现。
2. **本项目已有同类改动的先例**：v1 的能力头原本只读 256 维 LSTM 状态，加上编码器 pooled 摘要（`ability_head_hidden` 宽头 + `[state; pooled]`）后，测试 top-1 从 0.5990 提到 0.6130（扫描臂 0.6090／v3 0.6090 也都在这个位置）。选择解码器至今**只读 LSTM 状态**，与当时的能力头是同一个结构瓶颈。

## 唯一改动

`BCModelConfig.selection_uses_pooled`（默认 `false`，旧检查点照常加载）：开启后，选择解码器的初始隐状态由

```
[state ; ability_emb ; kind_emb]                     512 维
```

变成

```
[state ; ability_emb ; kind_emb ; pooled]            640 维
```

`pooled` 是编码器对当前步全部实体的掩码均值（`recurrent()` 已经返回，能力头早就在用）。GRU 每步的输入（`[previous ; ability_emb ; kind_emb]`）不变，`selection_hidden` 仍为 128——改动只增加 128×128 = 1.6 万参数，不改变解码器结构。

代码已就位（`src/scv_star/models/bc.py`），单测 `test_selection_can_condition_on_the_pooled_summary` 覆盖默认关闭与开启两条路径；`configs/experiments/bc-86383-v4.json` 已生成并用 2 步冒烟跑通。

## 判据（事前固定）

参照 v3 的**统一口径**验证数字：总损失 5.0955、选择损失 2.4223、top-1 0.6146、选择 F1 0.4423、recall 0.264。

1. **主判据**：验证选择损失 < 2.3723（改善 ≥0.05，约为验证噪声的 2 倍）。
2. **次判据**：验证总损失 < 5.0955，且 top-1 不低于 0.6146。
3. **测试**：只评估一次（验证损失最低的检查点），与 v3 的 5.3380、扫描臂的 5.3171 比较；只有总损失低于 5.30 才主张“改善”，否则按持平或失败记录。
4. 不换种子重跑；不根据测试分数挑检查点。

## 成本

- 训练：7,200 训练秒 + 验证开销，墙钟约 2 小时 20 分（v3 为 8,464.7 秒，含训练集评估）。
- 评估：单次测试评估约 5 分钟（批 2、新口径）。
- 代码：已完成，约 1 小时含测试。

## 风险与备选

- **风险**：选择错误可能主要来自“哪些单位该选”的匹配问题，而不是缺少全局上下文；若如此，加 `pooled` 只会小幅降低损失而不改 recall，判据会如实失败。
- **备选 A（若 v4 失败）**：正则化——v3 的训练子集 top-1 0.6818 对验证 0.6146，间隔 0.067（v1 只有 0.033），把 `dropout` 提到 0.2 或 `weight_decay` 提到 3e-4 是有依据的下一步，同样一次只改一项。
- **备选 B**：把目标单位头（24% 的总损失）作为目标，例如给指针查询加 `pooled`，与本次改动对称。
- 不建议同时改多项——v2 的教训就是一次改了三项，事后无法归因。

## 运行命令

```bash
TS=$(date -u +%Y%m%dT%H%M%SZ)
.venv/bin/scv-bc --config configs/experiments/bc-86383-v4.json \
  --output artifacts/runs/bc-86383-v4-$TS --device cuda --train-metrics

# 训练结束、验证最低点确定后，只做一次测试评估
.venv/bin/scv-bc --config configs/experiments/bc-86383-v4.json \
  --output artifacts/runs/bc-86383-v4-test-$TS --evaluate \
  --checkpoint artifacts/runs/bc-86383-v4-$TS/checkpoints/best.pt \
  --test-cache data/interim/bc-86383-v1-test --evaluate-batch-size 2 --device cuda
```

起跑前应按实测每步耗时复核 `lr_schedule.total_updates`（v3 实测 0.073 秒/步 → 96,026 步，余弦走了 90%）；若本次每步明显更慢或更快，改 `total_updates` 到“预算内步数”的 1.05 倍左右再起跑。

### 结论

1. **改动没有带来改善。** 验证总损失比 v3 高 0.037、测试总损失高 0.023，且**验证与测试方向一致**，不是噪声。选择头的 recall／F1 基本没动（recall 0.2976 vs 0.2965，F1 0.4435 vs 0.4423），损失反而略高——说明选择解码器缺少的**不是全局场景摘要**：它本来就通过 LSTM 状态间接看到了局面，再显式加一次没有新信息。
2. **能力头与点预测头反而略好**（ability 损失 1.1509 vs 1.1522；测试 top-1 0.6107 vs 0.6090；目标点 11.79 vs 11.91），但这些差异都在噪声内，不足以抵消选择项的退化。
3. **一个必须说明的混杂**：v4 只跑了 83,284 步（v3 是 96,026），因为中位步时从 0.0732 涨到 0.0808 秒。其中一部分是我在训练期间跑补齐步诊断（CPU 上加载 11 GB 缓存并做 599 次前向）抢占了 CPU。同一步数（65,000）比较仍然失败，所以结论成立，但“差 0.037”的量级被资源争用放大，不能当作精确效应量。
4. 按方案的事前约定：**不换种子重跑**，按失败记录。

### 下一步

`step_mask` 修复（补齐步不计入损失与指标）应在任何新一轮训练之前完成：它会改变训练目标与全部指标口径，历史运行需要重新给出新口径基线。之后才是备选 A（正则化）或其它方向。
